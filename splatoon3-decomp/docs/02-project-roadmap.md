# 2026-10-16 · Splatoon 3 源码还原：技术路线与 Agent 化设计

> 目标已明确：**还原 Splatoon 3 源代码**（不是为 RL 取几个内存偏移）。内存读取/注入
> 由其他人负责，我们的任务是静态逆向 + 反编译 + 匹配。这份文档是这个目标下的路线设计。

## 0. 必须先接受的三个事实

### 事实一：这是社区级十年的项目，不是一个人的项目

唯一的 Switch AArch64 反编译成功先例是 `zeldaret/botw`（旷野之息）。硬数据：

| 指标 | 数值 |
|------|------|
| 起始 | 2020-08 |
| 至今 | 6 年 |
| 星数 | 2,236 |
| 贡献者 | 38 人 |
| 但 | **一人提交 1,476 次**（leoetlino），第二名 74 次 |
| 完成度 | **17.49%**（函数 30.40%） |

也就是说：**目前全世界没有任何一个 Switch 游戏被完整还原过。** botw 是最接近的，
6 年、2 千人关注、38 个贡献者，也只做到 17%。而且 botw 有 Splatoon 3 没有的优势
——它有 Wii U 版的调试符号当跳板。

Splatoon 3 的体量只会更大（本体 XCI 5.1G + 更新 7.3G）。**实测 11.3.0 的 `main`
解压后 100.69 MB**（text 82.38 / rodata 82.38 / data 50.10 MB），函数数以万计。
**"完整还原 Splatoon 3" 在单人尺度下不可达**，这个预期必须先钉死。

### 事实二：匹配反编译有机械可验证的 oracle —— 这是 agent 化唯一成立的理由

反编译有两种：

- **非匹配（non-matching）**：产出语义等价的 C++，能编译能跑就行。问题：没有自动
  验证手段，只能靠人读。**这种模式下 LLM 会大量产出"看起来对"的垃圾。**
- **匹配（matching）**：产出的 C++ 编译后，**逐字节**等于原二进制。验证是机械的。

`objdiff`（587★）就是干这个的：把重编译产物和原函数做逐指令 diff，给出匹配百分比。
botw / ssbu-decomp 走的都是这条路。

**这一点决定了整个 agent 化设计**：匹配反编译给了一个**可计算的奖励信号**。函数级
任务因此变得像 RL —— 有 ground truth、可自动判定成败、可大规模并行。没有这个
oracle，"agent swarm 反编译" 就是 LLM 空转产幻觉。

### 事实三：匹配的前提是拿到**精确的编译器工具链**

要逐字节匹配，必须用**和目标二进制相同的编译器 + 相同版本 + 相同优化选项**。
Nintendo 用某个特定版本的 clang。这是全项目**最大的未知和头号关键路径**：

- 拿不到精确工具链 → 匹配率永远上不去 → oracle 信号失效 → agent 化失去意义
- 拿得到 → 整个流水线成立

所以**第一优先级的调研任务不是反编译任何函数，而是确定 clang 版本和编译选项**。
这通常通过"编译一个已知函数，调 flag 直到字节对齐"来反推。

## 1. 工具链（分层）

```text
[提取层]  hactool / nstool         NSP/XCI → NCA → ExeFS → main NSO   (本机有 prod.keys ✓)
   ↓
[转换层]  Ghidra-Switch-Loader     NSO → Ghidra 可识别（374★，活跃维护到 Ghidra 12.1.2）
          swspl                     NSO info/split/dump（11★，半停滞，仅作备份路径）
   ↓
[拆分层]  splat                     二进制 → 函数/段/符号清单（368★，活跃，支持自定义 loader）
   ↓
[分析层]  Ghidra 12.1.4 + JDK 21   反汇编 + 反编译 + 结构恢复
   ↓
[构建层]  clang（版本待定 ⚠️）     目标工具链 —— 匹配的关键
   ↓
[验证层]  objdiff                  逐指令匹配率（587★）—— oracle 信号源
   ↓
[组织层]  Git 仓库 + 符号/结构知识库 + 进度看板
```

已有的现成资产（几乎零成本）：

- `~/.switch/prod.keys` + `title.keys` ✓
- 金手指文件：24 个内存地址锚点（v11.0.1 的，需重定位）
- Flexlion `botinfo.json` / `fxconfig.json`：已暴露的数据模型（材质名表等）
- `DesperC/Awesome-Splatoon3-Hacking`：社区资源合集

**注意**：`decomp-toolkit`（311★）虽然是最成熟的 decomp 工具链，但它**只支持
GameCube/Wii，不支持 Switch**。Switch 目前没有等价的成熟模板，这是工具链缺口。

## 2. 技术实现方法

### 阶段划分

**Phase 0 — 可行性与地基（决定项目生死）**

1. ✅ **已完成**：用 hactool + nstool 从 11.3.0 更新 NSP 提取 `main` NSO。
   Build ID `28c4287aee36f749` 与运行时完全一致。详见 `03-extraction-verified.md`。
2. ✅ **已完成**：确认 `main` 是标准 NSO0（LZ4 压缩，flags=0x3f），解压后 100.69 MB。
   字符串显示自研引擎 + Havok 物理（`hk2021_1_8`）。LunchPack 待确认。
3. ✅ **已完成**：导出符号库种子（`symbols/`，5,376 个游戏自有名）。
4. ⬜ **下一步：反推 clang 工具链** —— 挑几个小函数，编译对比，调 flag 直到字节匹配。
   **这是头号关键路径。**
5. ⬜ 跑通 `splat` 拆分，产出函数清单。
6. ⬜ 搭 `objdiff` 验证回路，用 1 个函数验证"改写 → 编译 → diff"闭环。

**Phase 0 的产出不是反编译成果，而是一个能自动判定的流水线。** 这一步不通，
后面全是伪工作。

**Phase 1 — 骨架恢复**

- 从 rodata 字符串表导出类型/字段名（**已做**，见 `symbols/`：5,376 个游戏自有名）
- 恢复类结构（`spl::` 类名已知，需对应到 vtable 和构造函数）
- 恢复全局数据、字符串表
- 建立子系统地图（哪些函数属于 Player / Weapon / Game / Sequence…）

**Phase 2 — 按子系统匹配（这里才规模化）**

每个子系统独立成 PR，独立验证。优先选：
- 小且自包含的（数学库、容器、序列化）
- 有运行时线索能验证命名的（配合另一组人的内存读取/注入，确认字段语义）

**Phase 3 — 持续扩张**

### 符号现状（已实测，取代早前的推测）

**⚠️ 修正**：早前从 Flexlion 的 `subsdk0` 看到 19,209 个 `_Z` 符号，误以为游戏
"没被完全 strip"。**实测游戏本体 `main` 后，这个判断是错的。**

| 项 | 数量 | 性质 |
|----|------|------|
| `_ZN` C++ 符号 | 946 | ⚠️ **几乎全是 SDK 的**（`nn::` 命名空间） |
| 游戏自有 `_Z` 符号 | ~100 | 基本为零 |
| `spl::` 类名 | **2,027** | ✅ 在 rodata 字符串表里 |
| `spl__` 参数表名 | **1,855** | ✅ 字符串 |
| `game__` / `game::` | 379 / 92 | ✅ 字符串 |

原因：`subsdk0` 是 Flexlion 自己编译的模块（带完整符号），**不是游戏本体**。

**真实处境**：游戏自己的代码**没有 C++ 符号**（函数名全没了）。但 NintendoSDK 的
反射系统把**类型名和字段名保留成了 rodata 字符串**。所以：

- ✅ 类名可恢复（`spl::AttackEventMulti16` 这类是真的，可据此命名函数）
- ✅ 字段名可恢复（`spl__BulletBombMoveParam` 这类参数表名，配合 RomFS 参数文件互验）
- ❌ 函数名不可恢复（要靠 Ghidra 分析 + 交叉引用推导函数边界）

难度介于 botw（有 Wii U 版符号作跳板）和完全 strip 之间。**比最坏情况好，但远非
"有符号表"的轻松模式。**

## 3. Agent 化设计（重点）

### 核心思路：把"反编译"变成"有 reward 的并行任务"

匹配反编译的天然结构：**每个函数是一个独立任务，有机械的成败判定**。这正好是
agent 集群的完美形态——不是让 LLM 自由发挥，而是让它在**有 oracle 的闭环**里迭代。

### 为什么不是"扔一堆 agent 就完事"

- LLM 直接反编译的**语义正确率**在研究中仍是实验阶段（LLM4Decompile、DecompileBench
  等都是论文级，没有工业级验证）。**裸 LLM 产出的 C++ 不可信。**
- 真正有效的是 `Dryxio/reagent`（2,101★）的架构：**reverser → checker → fix 循环 +
  客观结构验证器 + 候选编译/测试门 + parity 判定（GREEN/YELLOW/RED）**。
  它的设计哲学就是"保守验证，不是语义等价的证明"——这个诚实的定位是对的。

### 推荐的集群架构

```text
                    ┌─────────────────────────────┐
                    │  共享知识库 (Knowledge Graph) │
                    │  · 已知类型/结构/枚举          │
                    │  · 已命名函数 + 证据           │
                    │  · 工具链配置（clang flags）    │
                    │  · 符号命名约定                │
                    └──────────┬──────────────────┘
                               │ 读写
        ┌──────────────────────┼──────────────────────┐
        ↓                      ↓                      ↓
   ┌─────────┐           ┌─────────┐           ┌─────────┐
   │ 反编译   │           │ 反编译   │    ...    │ 反编译   │  ← 函数级并行
   │ agent   │           │ agent   │           │ agent   │    (每函数一任务)
   │(reverser)│          │(reverser)│          │(reverser)│
   └────┬────┘           └────┬────┘           └────┬────┘
        ↓                     ↓                     ↓
   ┌─────────────────────────────────────────────────────┐
   │        机械验证层（唯一可信的裁判）                    │
   │  编译 → objdiff → 匹配率%                            │
   │  + 结构验证器（CFG/调用图一致性）                      │
   └─────────────────────────────────────────────────────┘
        ↓ 不匹配则回流
   ┌─────────┐
   │ 审查/修复 │  ← checker agent，不同模型/不同上下文
   │  agent   │
   └─────────┘
```

**关键设计点：**

1. **oracle 是编译+objdiff，不是 LLM 自评。** LLM 的自我评价一律不可信。
2. **reverser 和 checker 用不同模型 / 隔离上下文**（reagent 的做法），避免同源错误。
3. **知识库是瓶颈也是杠杆**：类型/结构恢复得越准，后面所有函数的匹配越快。
   知识库质量 > agent 数量。
4. **命名必须有证据**：botw 的 AGENTS.md 明确规定——"没有研究过的组件不重写，除非
   组件和大部分字段能被命名"。**宁可留着 `FUN_1234`，也不要编个假名。**
   假名会污染知识库，代价比不命名大得多。

### Agent 的效率边界（诚实评估）

- **agent 擅长**：函数级候选生成、命名建议、交叉引用分析、样板代码、批量分类。
- **agent 不擅长**：需要跨大量上下文推理的架构判断、编译器优化还原的艺术
  （botw 专门列了一堆"这看起来不像人写的，说明还有优化没还原"的规则）、
  需要创造性洞察的算法识别。
- **真正的瓶颈不是 LLM 吞吐，而是**：(a) clang 工具链的精确还原；
  (b) 类型/结构知识库的积累速度；(c) 人的审查带宽。

botw 的 AGENTS.md 已经承认他们在用 AI agent（要求 commit 里披露模型和厂商），
但**所有 PR 必须人工审查**。这是当前最务实的定位。

## 4. 现实的范围建议

**不要定"还原 Splatoon 3"为目标**，定不了、测不了、做不完。建议改成：

> **目标：为一个自包含的子系统建立完整的"提取 → 反编译 → 匹配 → 验证"闭环，
> 并产出该子系统的可编译、高匹配率的源码。**

候选子系统（按可行性排序）：

1. **数学/容器/序列化库**——自包含、无游戏逻辑依赖、函数多但简单，最适合验证
   工具链和 agent 流水线。
2. **参数/数据表加载**（BYAML / 游戏参数）——能和社区 datamining 成果互验命名。
3. **某个具体武器的机制**——有确定性语义，好验证。

跑通一个子系统后，再决定要不要扩张。**这个决策点才是应该花时间的**，不是一上来
投三个月搭巨型集群。

## 5. 立即可做的下一步（按优先级）

1. **提取 `main` NSO**（hactool，本机 keys 齐全，零安装）——先看真实规模。
2. **确认引擎与符号保留程度**——决定难度基调。
3. **反推 clang 版本**——项目生死线。
4. **搭 objdiff 单函数闭环**——验证流水线成立。
5. 之后才谈集群和扩张。

## 6. 与现有仓库的关系

现有的 `splatoon-rl-lab`（视觉/RL）和这个是**两个不同目标的项目**。按仓库约定
（一个 idea 一个子文件夹），源码还原应该**开新文件夹**，例如：

```text
splatoon3-decomp/     # 反编译项目：工具链、符号库、匹配源码
  README.md
  tools/              # 提取、拆分、构建脚本
  symbols/            # 符号/类型知识库
  src/                # 匹配的反编译源码
  docs/               # 研究笔记、进度
```

两者共享的只有游戏文件和对游戏机制的理解，不共享代码。

## 7. 边界

- 只做私有、离线、自有文件的实验。
- 反编译产物**不公开分发**（Nintendo 代码）；botw 的 README 也是明确声明
  "不包含游戏资产，不能用来玩"。
- 定位是研究/互操作性/理解游戏内部，不是制作作弊器或盗版。
