# run74：my-demo-002 卡顿与 X 地图

范围：只改人工录制输入/预热/诊断，不改游戏逻辑、原存档、policies、正式 arena/T1/A8 宿主，不训练。所有原件、原生截图、编译清单和复现记录留在私有 `work/`。

## 原件与归因

原录制 `work/rl-demo/my-demo-002`：11509 present，到 Winners；HUD 5杀2死、玩家涂地25.3%。原生会话 `work/tests/m6-2p-20261025-155813-201875`。使用既有 `ink-recording-host-r1/dmhost-demo`，SHA256 `9a304a650a65ae35bf92f85eb93a24121f7a3d7080559b69aa89800ff05740bc`；本轮未重编任何宿主。

**主因是战斗中第一次编译 Metal 着色器/管线；双进程逐帧屏障把对手的编译停顿也传给人玩窗口。** 指定的旧脚本预热目录实际上只有角色0的15条用户清单、角色1的17条。宿主确认角色0只预热14个shader、1条render pipeline；这不覆盖人的游走、潜墨、受击、死亡、重生及地图等路径。磁盘缓存也不代表进程内全部管线已载入。

`timing.jsonl` 与 `native-barriers.jsonl` 按实际 native frame 对齐，再查双方 `nvn.tsv` 和 `host.log` 的长帧创建耗时（gfx标签通常比ACK小1，报告保留相邻帧窗口）：55次ACK>100ms，全部有相邻帧创建新shader/pipeline且创建耗时>50ms的原生记录。55次ACK累计27.808秒；并行编译累计时间会重叠，不能相加冒充独占墙钟。

`trace.json`在相同帧给出实际位置/形态/HP和事件：如190在出生后潜墨移动，885/890在中路潜墨，3473起连续受击且3486倒下，2354对手已倒下/回出生。它用于确认这些是正常游戏过程中的停顿，不把某个事件名称直接当成GPU耗时证据。

排查其他来源：

- 客户端sample→send中位0.171ms、p99 1.417ms、最大47.495ms；前次ACK→下次sample p99 0.617ms、最大5.175ms。录制JSON写入/刷新、Python GC、策略计算、SDL轮询不解释这55次宿主ACK内部的长等候；原始IMU仍保留，不宣称USB到光子延迟已测。
- 周期墨图仍为同队列异步5.12MB复制、GPU完成后后台PNG。原件 `DEMO_INK_ASYNC io_ns` p99 28.59ms、最大38.77ms；这是后台编码耗时，不是录制线程同步等候。对手进程不开周期读回，仍出现秒级编译长帧。相同 `--ink-every 30` 热重放用于进一步区分；没有通过关掉墨图掩盖问题。
- 原生长帧中GPU活跃通常约10–18ms，贴图上传常为0；单帧几百ms至1.7s主要在库/管线创建及对端屏障。没有用强制present interval或游戏慢放冒充实时。

## 修复

1. `--warm-from`复用最近的完整人玩覆盖，而非仅复用短脚本。`warmup.assemble`合并继承链及两个视角的已遇到S/R/C内容键，去重但不改原清单，生成每角色 `warm-N.tsv` / `warm-N.json` 来源与数量审计。启动打印实际预热规模；格式错误拒绝。
2. 先以002清单同输入热重放：预热835 shader/1265 render/8 compute，1.29秒；55次>100ms降为4次（189–552ms）。这4次仍为未覆盖的首次编译，新增18条shader记录（两角色有重合），保留为第一轮诊断，没有冒充目标通过。
3. 纳入新覆盖和地图夹具，双方均预热885 shader/1331 render/8 compute，再完整重放相同002逐present输入。输入仍标记scripted fixture，不伪装为第二份人类示范。最终数值见下表及本轮私有报告。

这是一份**已观察覆盖的预热修复**，不是穷举所有未来特效的证明；换地图/武器/模式或出现新效果仍可能首次编译。后续录制应沿用最新完整局的 `--warm-from` 继承链，不回退到旧短脚本目录。加载期预热与受控对战分开统计。

## X：物理输入到原生地图

002的profile已含印字X=SDL button2，且X不在primary_only屏蔽项。问题发生于随后：`GAME_BUTTONS`只有ZR/ZL/R/RS/B/Y，controller→capture→DemoClient丢失了X。原生渲染未缺地图层。

修复使用demo专属 `observer_buttons=[X]`：Controller保留原始/处理后观测键，capture记录并传递，DemoClient注入`nn::hid`的X bit2；primary_only只屏蔽R/RS。六个原有训练按键、正式NativeParallelEnv动作空间不变；正式入口仍拒绝demo。

原生离线夹具 `run74/minimap-r1` 在540–659帧按X，`player-0/screenshots/frame-600.png`及1200帧截图均可见全地图（X是切换键，B没有关闭，后续夹具改为再次按X关闭）。截图已本机目视，不提交。新 `--script-pattern minimap` 在900帧再次按X，截图功能独立于额外墨图调查，不污染性能复现。

BC转换仍不学习X：量化标签不变，另记录 `unrepresented_X`。它是人类观察操作；使用X片段训练前需按输入/地图状态明确处理，不能把没有X动作头的策略宣称能学会按X。没有本轮训练或重新给示范数据签发ready_for_training。

## 验证与性能

第二轮最近局清单进一步降至2次>100ms，但仍是对手新库（243.7/202.1ms创建），不是读取墨图。于是补充本机2716份历史`pso_user.tsv`中的**S-only**已遇库，共1681个；没有引入所有历史R管线（当前1332/1333条，低于2048缓存容量），也没有加载整套27275份shader反射。首次广覆盖后台预热角色0用121.806秒，后续记录按初始暂停屏障等待双方完成，完成前不交出用户操作。新的`warmup.wait_ready`支持超时、退出、取消、资源错误；不推进任何中立游戏帧，不改时钟步长。缓存热后原生地图复测初始等待约1.5ms。

R3完整到Winners、11509帧、无>100ms，最长49.714ms；逻辑全程1%low40.499、对战46.024fps。显示全程1%low38.774、热段39.484fps，仍略低40，因此另测关闭逐NVN调用计时包裹器的R4候选。R4前段正常，9326帧起出现无编译的GPU/提交等待尖峰（GPU区间可达352.6ms，ACK最大3009.2ms），故通过本轮STOP保存并取消；此候选没有采纳，默认计时配置完整恢复。其资源记录pressure=1、新增swapout=0，现有证据不足以把异常因果归给开关或外部调度，不能猜称已定位。没有把R3显示指标低于目标或R4失败删掉。
